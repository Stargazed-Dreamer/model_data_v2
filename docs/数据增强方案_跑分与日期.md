## 1. 跑分补全方案

### L0 · 本地批量，零网络成本（**建议先做**）

**数据源**：`external_sources/epoch_benchmark_data/*.csv`

实测：75 个文件 / **2,417 行有效数据 / 619 个去重模型**。
⚠ 坑：列名不统一，至少存在 `Percent correct` / `EM` / `Score` / `Accuracy` 等多种分数列，只认一种会漏掉 97% 的数据（实测只认 `Percent correct` 时仅 72 行，补全列名后 2,417 行）。

**收益（实测）**：
- 主库 900 条中**精确匹配 188 条（20.9%）**；
- 其中 **34 条当前完全没有 independent 跑分** → 直接补；
- 命中集中在大厂：OpenAI 35 / Alibaba 26 / Anthropic 21 / Google DeepMind 18 / Microsoft 8 / xAI 8 / Meta AI 7 / DeepSeek 6 / Mistral 6。

**成本**：写脚本 1 个（映射 + 归一 + 生成 incoming 文件），跑一次几分钟，**不消耗任何网络采集**。
**产出形态**：按现有合并规矩，生成 `incoming/models/` 下的补丁文件，走 `model_data_tool.py merge`，**数组策略必须是并集不是 replace**（§18 事故）。

### L1 · 网络批量（中等成本）

| 源 | 目标段 | 状态 | 说明 |
|---|---|---|---|
| LMArena / DataLearner 镜像 | `arena_elo` | ✅ **D39 已做** | 实测：主榜有 JSON API（400 条），分类榜需解析 flight 流；已补 296 条 / 172→215 条记录。**未翻倍**——瓶颈不在抓取，而在主库大量模型根本没上过 LMArena（长尾/小厂/base 模型） |
| Artificial Analysis | `independent` | ❌ 实测受限 | `api/v2/data/llms/models` 返回 **401 需 key**；若要接需先申请 API key |
| OpenCompass | `independent` | 待验证 | 国内模型覆盖好，能补 Alibaba/DeepSeek/Zhipu/Moonshot |
| SuperCLUE | `independent` | 待验证 | 中文能力维度，补国内模型 |

### L2 · 官方自报回补（高成本，逐模型）

针对 235 条"完全无跑分"的记录：按 P0 厂商逐个回官方发布稿 / 技术报告 / Model Card 抄自报分。
收益是 `self_reported`，**不可横向比较**，但能让空记录有内容。建议只对 P0 厂商旗舰做，长尾不做。

### L3 · 结构性现实（建议接受）

独立评测天然只覆盖头部模型。剩下一批长尾模型（尤其开源小厂）**永远不会有 independent 分**。
建议：不硬凑，而是在这些记录上明确标注"无第三方评测"，让下游分析知道这是**覆盖缺失**而非"模型差"。
⚠ 硬凑的代价：把不同方法论的分数混进 `independent`，会毁掉这个字段唯一的跨模型可比性。

### 跑分补全的四个风险（必须先定规矩再动手）

1. **benchmark 名归一**：epoch 的 `mmlu` 与库里的 `MMLU`、库内 41 种 `source_type` 写法同类的老问题。先出一张 `benchmark` 名称映射表再导入。
2. **score_type 归一**：epoch 多为百分制，库内口径是 0–1 小数（执行细则 §10），必须换算并在 `notes` 标注。
3. **主键冲突**：并集主键 `benchmark, config, date`（`independent` 加 `source_site`）。epoch 条目缺 `config` 时填 `default`，`date` 取 CSV 里的 `Release date` 还是评测日需统一。
4. **source 标注**：epoch 条目统一 `source_type="独立评测平台"`、`source_site="epoch.ai"`、`confidence="T1"`、`source_url` 取 CSV 的 `Source link`（部分行该列为空 → 这些条目降级 `T3` 或丢弃，需拍板）。

## 2. 发布时间精确化方案

### 核心思路：为每家厂商固化一个「官方台账页」

**范本已找到并验证**：阿里云百炼《模型上下架与更新》
`https://www.alibabacloud.com/help/tc/model-studio/newly-released-models`
——逐条列出「日期 + model_id + 说明」，实测含 `qwen3.8-flash`(2026-08-26)、`qwen3.8-max-0902`(09-02)、`qwen3.8-27b`(08-17)、`kimi-k3`(08-19)。
**这是唯一能同时给出精确日期和官方身份的源形态**，应作为采集日期时的第一选择。

**待建的台账页映射表**（P0 厂商，逐个探一次并固化到 `跟踪源清单.md` §1-B）：

| 厂商 | 台账页候选 | 状态 |
|---|---|---|
| Alibaba/Qwen | `https://www.alibabacloud.com/help/tc/model-studio/newly-released-models` | ✅ 已验证 |
| Meituan | `tech.meituan.com`（技术团队博客，逐篇带日期） | ✅ 已验证 |
| OpenAI / Anthropic / Google / Meta / Mistral / xAI | 各自 news 页 | 待探（见 `跟踪源清单.md` §1-B） |
| 其余 | 开放平台"更新日志 / 版本记录 / release notes"页 | 待探 |

### 已验证的辅助日期源（带风险）

| 源 | 能精确化的量（实测） | 风险 |
|---|---|---|
| **epoch_ai_models/*.csv** 的 `Publication date` | 主库匹配 **453 条**；其中能把"只到月"精确化 **318 条** | ⚠ **有错值**：deepseek-chat 主库 2024-12，epoch 给 2025-12-01（差 1 年）。**必须先抽样校验** |
| epoch benchmark CSV 的 `Release date` | 只到月的 532 条中覆盖 144 条 | 同上 |
| OpenRouter `created` | 435 个模型全覆盖 | ⚠ 是**上架日**，实测 LongCat-2.0 发布 06-30 / 上架 07-20，**滞后 20 天**，只能当下界 |
| HF `createdAt` | 全开源模型 | ⚠ 常**早于**发布日（Qwen3.8-Flash-Next 建库 08-24 / 发布 08-26） |

### 建议执行顺序

1. **先抽样校验 epoch 日期**：随机抽 30 条，人工核对官方日期，统计错误率。
   - 错误率 < 5% → 批量采纳；
   - 5%–15% → 只采纳"与现有月份一致"的那部分（即只补日、不改月），安全且能拿下一大半；
   - \> 15% → 只作参考，不做批量写入。
2. 建 P0 厂商官方台账页映射表（一次投入，长期复用）。
3. 对 epoch 覆盖不到的记录，按厂商逐个回官方源确认。

### 一个待拍板的 schema 问题

现在无法区分"2026-08 是精确到月"和"2026-08 是只知道月份"。建议二选一：
- **A（零改动）**：在 `meta.notes` 写「日期精度：月，来源 X」；
- **B（需 schema 升级）**：新增 `basic_info.release_date_precision`（`day` / `month` / `quarter`）+ `release_date_source`。
B 更干净但要动 schema 和门禁，属于结构性改动，需要单独拍板。
