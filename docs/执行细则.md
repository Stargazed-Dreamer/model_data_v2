# 主流大模型静态数据采集 · 执行细则（十项统一规范）

> **配套文件**：`prompt.md`（v2 工作 prompt，含 7 项核心决策与 schema 1.1 字段定义）
> **文档定位**：用户在 v2 确认时可自行拍板的 **10 项执行层面细则**，独立于工作 prompt 单独成文，作为采集 agent 的「如何填」补充规范。
> **层级关系**：本文档与 `prompt.md` 不冲突、只细化。凡本文档更具体的写法（如 `source_type` 细分、分批格式）以本文档为准；其余仍以 `prompt.md` 为准。

## 1. 参数量未披露时的处理

**问题来源**：A 问题3、B 问题3、C 问题2
**对应字段**：`architecture.total_params_b`、`architecture.active_params_b`、`architecture.notes`

### 规则
- 官方未披露参数量时，`total_params_b` 与 `active_params_b` **一律填 `null`**。
- 必须在 `architecture.notes` 注明「官方未披露参数量」。
- **所有厂商统一执行**，不留 `0`、不留空字符串 `""`、不填任何估算值。
- MoE 模型：总参 / 激活均按此规则（都 `null` + notes）。

### 执行示例
```json
"architecture": {
  "total_params_b": null,
  "active_params_b": null,
  "architecture_type": "Unknown",
  "notes": "官方未披露参数量"
}
```

### 边界
- 即便行业普遍认为「约 X 亿参数」，只要官方未确认，必须 `null` + notes，不得填估算值（估算值不可信，会污染横向对比）。
- 若官方披露了激活参数但未披露总参数（或反之）：已披露项填数字，未披露项 `null` + notes 说明「仅披露激活/总参数」。

## 2. 上下文窗口：标称 vs 有效

**问题来源**：A 问题4、B 问题7、C 问题8
**对应字段**：`architecture.context_window_tokens`、`architecture.context_window_effective_tokens`、`architecture.notes`

### 规则
- `context_window_tokens`：填官方**标称**上下文窗口（如 200000、1000000）。官方同时给了「原生 X / 可扩展到 Y」时，填**最大可支持值 Y**，并在 `notes` 写明 X 为原生、Y 靠什么手段扩展。
- `context_window_effective_tokens`：填**实际可用**的上下文窗口。**不要求独立第三方实测** —— 厂商标称值、厂商自测值、社区实测值都允许填，谁给的数字写在 `notes` 里；查不到任何依据才留 `null`。
- 这一栏表达的是「官方支持到多长」，不是「多长以内效果不掉」。长文尾端召回衰减是普遍现象，用 `notes` 记证据，不要靠调小这个数字来表达。
- 有效值**不得大于**标称值（门禁会 WARN，见 §2 边界第 2 条）。

### 执行示例
```json
"architecture": {
  "context_window_tokens": 272000,
  "context_window_effective_tokens": 272000,
  "notes": "有效值取官方 API 上限（未独立实测）；社区反馈约 272K/95% 软限制，长文尾端召回下降"
}
```

### 边界
- `context_window_tokens` 永远填官方标称值，不得因「有效更短」而改小标称。
- `context_window_effective_tokens > context_window_tokens` 一定是填错了栏位（最常见：把厂商的可扩展窗口塞进有效栏、原生值留在标称栏），按上面第一条归位。
- **口径修订记录（2026-08-30）**：原规则为「未经独立测试（T1）验证一律填 `null`，仅当有 needle-in-haystack 一类 T1 评测才填数字」。全库实测与该规矩背离 —— 208 条填了有效值，其中 173 条就是标称值的原样抄写，门禁为此挂了 127 条警告。用户拍板：厂商标称值不算说谎，差别只在尾端效果，故 173 条**原样保留**、本规矩**废止**。

## 3. 多模态 `false` vs `null` 的判定

**问题来源**：C 问题6、B 问题6
**对应字段**：`modality.input.*`、`modality.output.*`、`modality.native_multimodal.*`、对应 `notes`

### 判定流程
1. 官方文档**明确支持** → `true`
2. 官方文档**明确「不支持 / 无此能力」** → `false`
3. 官方**未提及 / 描述模糊 / 仅第三方声称** → `null`，并在 `notes` 说明「实现方式未明确披露」
4. 经**工具链 / 外挂**支持（如 OCR、Whisper）→ `input.xxx = true`，但 `native_multimodal` 对应字段为 `false` 或 `null`，并在 `notes` 注明「外挂 OCR / 外挂语音」

### 执行示例
```json
"modality": {
  "input": {
    "text": true, "image": true, "audio": false, "video": null,
    "pdf": true, "code": true, "web": false,
    "notes": "PDF 经外挂解析；视频输入官方未提及，未明确披露"
  },
  "output": {
    "text": true, "code": true, "image": false, "audio": false, "speech": false,
    "notes": null
  },
  "native_multimodal": {
    "input_image": true, "input_audio": false, "input_video": null,
    "output_image": false, "output_audio": false,
    "notes": "图像原生；视频理解未明确披露；PDF 为工具链支持"
  }
}
```

### 边界
- **`false` 与 `null` 语义不同**：`false` = 官方确认不支持；`null` = 未知 / 模糊。
- 严禁用 `false` 代替「没查到」——没查到是 `null`。

## 4. 定价缓存 / 批量字段的采集优先级

**问题来源**：A 问题5
**对应字段**：`pricing.cached_input`、`pricing.cache_write`、`pricing.batch_input`、`pricing.batch_output`

### 规则
- 这四个字段为**必采字段**，不能因为只有标准价（`input`/`output`）就整体省略。
- 模型确实有缓存 / 批量价 → 填具体数字。
- 无官方精确值 → 填 `null`，并在 `pricing.notes` 说明媒体折扣信息，如「媒体提及 Batch API 约 5 折，但无官方精确单价」。

### 执行示例
```json
"pricing": {
  "currency": "USD", "unit": "per_million_tokens",
  "input": 5.0, "output": 30.0,
  "cached_input": null, "cache_write": null,
  "batch_input": null, "batch_output": null,
  "free_tier": null,
  "effective_date": "2026-08-01",
  "source_url": "https://openai.com/api/pricing",
  "source_type": "官方定价页", "confidence": "T0",
  "notes": "媒体提及 Batch API 约 5 折，但无官方精确单价；cached_input/cache_write/batch_* 暂缺官方值"
}
```

### 边界
- 即使四个字段全为 `null`，它们**也必须出现在 JSON 中**（不得省略字段名）。
- `cached_input` 为缓存**读取**价，`cache_write` 为缓存**写入**价，语义不同，不可混填。

## 5. 跑分多源冲突的记录方式

**问题来源**：C 问题4
**对应字段**：`benchmarks.self_reported[]`、`benchmarks.independent[]`

### 规则
- 同一 benchmark 在 `independent` 数组中**可有多条记录**（不同平台、不同分数），全部保留并逐条标注 `source_url` / `source_type` / `confidence`。
- `self_reported` 同理（若多份发布稿出现不同自报分）。
- 在对应对象或 `notes` 中注明「不同独立评测平台方法论不同，分数不可直接比较」。
- **不合并取平均、不强行统一为单值**。

### 执行示例
```json
"independent": [
  {
    "benchmark": "GPQA Diamond", "score": 0.78, "score_type": "accuracy", "config": "default",
    "date": "2026-07", "source_url": "https://artificialanalysis.ai/",
    "source_type": "独立评测平台", "confidence": "T1", "gap_to_self_reported": -0.04,
    "notes": "Artificial Analysis 口径"
  },
  {
    "benchmark": "GPQA Diamond", "score": 0.80, "score_type": "accuracy", "config": "default",
    "date": "2026-07", "source_url": "https://opencompass.org/",
    "source_type": "独立评测平台", "confidence": "T1", "gap_to_self_reported": -0.02,
    "notes": "OpenCompass 口径；与 AA 方法论不同，分数不可直接比较"
  }
]
```

### 边界
- 多源并存时，分析端应并列展示；数据集（本报告）只负责完整保留 + 标注方法论差异。
- 与 v2 冲突处理规则一致：T1 平台间冲突属正常，分别记录不合并。

## 6. 媒体转述来源的标注细分

**问题来源**：A 问题2、B 问题1
**对应字段**：所有 `source_type`、`confidence`、`notes`

### 规则
在 `source_type` 中固化以下细分项（与 `prompt.md` 步骤3 来源类型下拉对齐，并补全其余两项）：
- `"行业媒体转述官方发布"` — 媒体转述厂商官方发布稿（发布新闻、技术报告摘要）
- `"行业媒体转述独立评测"` — 媒体转述第三方评测结果
- `"官方技术报告（转述）"` — 无法直接访问官方报告、引用其转述版本

`confidence` 按实际**可访问**来源层级填写：
- 媒体转述官方发布稿中的自报分 → **`T0-自报-转述`**（不得标 `T0-自报`，见 v2 决策 2）
- 媒体转述独立评测 → 对应 `T3`（媒体层级）或沿用原始评测等级
- 官方技术报告（转述）→ 仍属转述，按媒体层级 `T3`，其中自报分标 `T0-自报-转述`

### 执行示例
```json
{
  "benchmark": "GPQA Diamond",
  "score": 0.942,
  "source_url": "https://example-media.com/opus-4.7-release",
  "source_type": "行业媒体转述官方发布",
  "confidence": "T0-自报-转述",
  "notes": "经媒体转述官方发布稿，官方技术报告不可直访"
}
```

### 边界
- `source_type` 与 `confidence` 必须自洽：转述来源不得配 `T0` / `T0-自报`（唯一例外是可直访的官方自报）。
- 与 v2 决策 1/2 联动：凡降级采集，必须在 `meta.notes` 声明「官方域沙盒不可访问，数据经媒体转述间接核实」。

## 7. 模型分批返回策略

**问题来源**：B 问题7
**适用**：长响应受限时的 JSON Lines 输出

### 规则
- 每批 **8–12 条**模型记录（按**厂商聚合**，同一厂商尽量放同一批）。
- 每条 JSON 对象**压缩为单行**（不展开多行）。
- 每批末尾输出一行 `// 剩余记录数: N` 注释（不计入 JSON 数据，解析时忽略）。
- 末批不足 8 条也正常输出；剩余 0 条时注释写 `// 剩余记录数: 0`。

### 格式示例
```jsonl
{"schema_version":"1.1","model_id":"openai:gpt-5.6:sol", ...}
{"schema_version":"1.1","model_id":"openai:gpt-5.6:terra", ...}
... (共 8–12 条，均为单行)
// 剩余记录数: 23
```

### 边界
- 批内不跨厂商硬性拆分（一个厂商记录分散在多批也可，但优先聚合）。
- 注释行以 `//` 开头、单占一行、置于该批最后一条之后。

## 8. 退役 / 已下线模型的 `verification_status` 建议

**问题来源**：C 问题7（v2 决策 5 已落地，本条为执行强调）
**对应字段**：`meta.verification_status`、`meta.notes`

### 规则（执行建议）
- 退役但 **API 仍可调用的模型** → `verification_status = "已过期"`。
- 完全下线、**不可调用的模型** → 仍收录并保留记录，`notes` 标「已下线，仅保留历史记录」，`verification_status` 可标 `"已过期"` 或 `"待验证"`。
- 与 v2 决策 5 一致：**不区分是否退役，尽可能全量采集**，不限制时间范围。

### 执行示例
```json
"meta": {
  "collected_at": "2026-08-24",
  "verified_at": null,
  "verification_status": "已过期",
  "source_urls": ["https://openai.com/api/docs/legacy"],
  "notes": "已下线，仅保留历史记录"
}
```

### 边界
- 是否采集、采集到哪个时间点 → 已由决策 5 拍板（全量、不限时间），本条仅规范状态字段写法。
- 现役模型标 `"已验证"` / `"待验证"` / `"存疑"`，不与退役规则混淆。

## 9. 产品线重叠时 `positioning` 的填写

**问题来源**：C 问题10
**对应字段**：`basic_info.positioning[]`、`basic_info.notes`

### 规则
- `positioning` 为**数组**，可多选官方定位标签。标签枚举：`旗舰` / `中端` / `轻量` / `推理增强` / `多模态` / `工具调用增强`。
- 按官方定位如实填写多个标签，如 `["旗舰", "推理增强"]`。
- 新旧旗舰重叠时（如旧旗舰仍默认、新旗舰已发布），在 `notes` 补充「当前默认 vs 新旗舰」的实际使用场景说明。

### 执行示例
```json
"basic_info": {
  "full_name": "GPT-5.2",
  "version": "5.2",
  "vendor": "OpenAI",
  "release_date": "2025-12",
  "positioning": ["旗舰", "推理增强"],
  "access": { "open_weights": false, "api": true, "local_deployment": false, "notes": null },
  "notes": "GPT-5.6 发布后，GPT-5.2 仍作为默认中高性价比主力，新旗舰为 GPT-5.6 Sol"
}
```

### 边界
- `positioning` 不允许为单字符串——必须是数组，哪怕只有一个标签也用 `["旗舰"]`。
- 标签以官方自述为准，不自行发明新标签（如需新增应回到规范层面讨论）。

## 10. 百分制转小数、日期、汇率等执行细节

**问题来源**：A/B/C 多处
**对应字段**：分数 `score` + `notes`、所有日期字段、价格 `currency` + `notes`

### 规则
- **百分制 → 小数**：原始为百分制（如 94.2%）的分数，除以 100 后填入 `score`（如 0.942），并在 `notes` 注明「原始为百分制，已除以 100」。
- **日期统一 ISO 8601**：
  - 精确到月：`2026-08`
  - 精确到日：`2026-08-24`（定价 `effective_date`、采集 `collected_at` 等需精确到日）
- **价格统一 USD**：
  - 非 USD 价格需按采集日期汇率换算为 USD，`currency` 填 `"USD"`，并在 `notes` 记录原始货币与汇率日期，如「原始 ¥50/百万 token，按 2026-08-01 汇率 7.13 折算为 USD 7.0」。
  - **汇率必须有可查来源，禁止使用假设值/估算值**（P4 修复）：汇率应取自采集当日公开可查的权威来源（央行/外汇交易中心公布汇率、主流财经数据平台的当日牌价等），并在 `notes` 中一并注明汇率来源与日期，如「汇率取自 XX 2026-08-01 中间价 7.13」。无法查到采集日汇率时，取最近可用日期的汇率并如实注明实际采用的日期；完全无法核实汇率时，保留原始货币价格入 `notes` 并将 USD 字段填 `null`，不得凭印象折算。

### 执行示例
```json
// 百分制转小数
{ "benchmark": "GPQA Diamond", "score": 0.942, "notes": "原始为百分制 94.2%，已除以 100" }

// 非 USD 价格换算（currency 仍为 USD，原始信息入 notes）
"pricing": {
  "currency": "USD", "unit": "per_million_tokens",
  "input": 7.0, "output": 21.0,
  "effective_date": "2026-08-01",
  "notes": "原始 ¥50/百万 token，按 2026-08-01 汇率 7.13 折算为 USD 7.0"
}
```

### 边界
- 所有 `score` 优先用 0–1 小数；百分制必须转小数 + notes 标注，禁止在 `score` 直接填 94.2。
- 汇率日期必须与 `collected_at` 或 `effective_date` 同源，避免口径混乱。
- **Arena 快照日（`benchmarks.arena_elo[].date`）按子榜源发布频率取值，允许月级**：text / coding 等日更子榜记为 `YYYY-MM-DD`；math 等仅月更子榜记为 `YYYY-MM`（如 `2026-08`）。校验器不强制 arena 日期日级，属正常口径差异，下游按子榜分别解读。

## 11. 执行清单（每条记录采集前 / 自查用）

合并上述 10 项，作为单条记录的快速自查：

- [ ] 参数量未披露 → `total_params_b`/`active_params_b` = `null` + notes「官方未披露」？
- [ ] 上下文 → 标称填 `context_window_tokens`（有扩展窗口的填最大值）；有效栏 `context_window_effective_tokens` 不要求独立实测，但出处写进 notes，且**不得大于标称值**？
- [ ] 多模态布尔 → `true`/`false`/`null` 判定正确（官方不支持=`false`，未提及=`null`）？外挂能力已 notes 说明？
- [ ] 定价 → `cached_input`/`cache_write`/`batch_input`/`batch_output` 四个必采字段均在（无论 null 与否）？
- [ ] 跑分多源 → 同 benchmark 多平台记录均保留，未合并取平均，notes 注明方法论差异？
- [ ] `source_type` → 媒体转述已用细分项（行业媒体转述官方发布 / 独立评测 / 官方技术报告（转述））？`confidence` 与来源自洽（转述不配 T0/T0-自报）？
- [ ] 分批输出 → 每批 8–12 条、单行、末尾 `// 剩余记录数: N`？
- [ ] 退役模型 → API 可用标「已过期」；完全下线 notes 标「已下线」？
- [ ] `positioning` → 数组多选、标签在枚举内、重叠时 notes 说明默认 vs 新旗舰？
- [ ] 格式 → 百分制已转小数 + notes；日期 ISO 8601；非 USD 已换算 + 汇率日期？

## 附录 A：已知风险（需向分析端提示，不改规范）

以下问题**暂不构成规范修改需求**，但影响数据质量，在后续分析报告中需显著声明：

1. **官方域不可访问是环境限制，非规范缺陷**。即使已批准降级策略，数据集中大量记录可信度低于严格 T0/T1，分析报告必须显著声明这一点。
2. **社区反馈的异常信号**（如 Opus 4.7 在 NYT Connections Extended 上从 94.7% 跌至 41.0%）不纳入规范基准，但在相应记录 `notes` 中保留风险提示，避免后续被误读为能力倒退。
3. **OpenAI 定价频繁变动**（如 Luna 降价 80%）意味着 `pricing.effective_date` 必须精确到日，且采集 30 天后需复核。
