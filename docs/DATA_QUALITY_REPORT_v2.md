## 〇、一句话结论 + 总评分

**这是一份「身份 + 参数 + 一堆 Arena 分数」的稀疏骨架，不是成品模型数据库。** 941 条里有 553 条（58.8%）连「定价 / 多模态 / 跑分 / 定位」任何一项都没有；98.4% 的记录 notes 里塞的是「待补 / 未含 / 未披露」之类的占位符，本质是在声明"我没采到"，而不是数据本身；2 条被标「已验证」的记录其实没有任何验证时间，属于假验证。

**总评：30 / 100（D−，不及格）。**
若只算用户真正要的「内容字段」（定价 / 多模态 / 跑分 / 定位），平均填充率仅约 **18 / 100**。

> 不是"全是垃圾"——定价抽样可信、Arena ELO 真实、model_id 零重复，这些亮点是真的。但作为「v2 数据库」对外宣称的完成度，**远不及格**。

## 二、🔴 致命问题 1：184 个 ERROR 的归因被现有报告歪曲

官方校验器复跑结果：`941 条，ERROR 184 项（涉及 17 条记录），WARN 107 项`。

`盘点与待改清单.md` 第八节原话是：

> "ERROR 184 项……**其余 174 项均为基座 v1_clean 骨架结构性缺失**（缺顶层键 / modality / pricing 四必采 / positioning），**属阶段0 设计、留待阶段3 质检**"

**这句话是错的，而且是在淡化问题。** 我做了两项独立核对：

1. 单独校验 `model_data_v1_clean.jsonl` → **0 ERROR / 0 WARN**。基座本身是干净的。
2. 把 184 个 ERROR 逐条归因（按 model_id 是否属于 v1_clean）：

| ERROR 来源 | 记录数 | 说明 |
|-----------|--------|------|
| **新增记录（v2 比 v1 多出来的 17 条）** | **15 条含 ERROR** | 即 184 错几乎全在这里 |
| 基座记录（v1_clean 已有） | 仅 2 条（各因 p2 空 URL） | 见第三节 |

ERROR 类型直方图（184 项）：

- `缺顶层必备键`：**70 项**（全在 15 条新增记录）
- `modality.* 缺失 / pricing.* 必采键缺失`：**89 项**（全在 15 条新增记录）
- `independent 缺 source_url`：**10 项**（已知 p2 空 URL 问题，跨 3 条记录）

**结论：184 错 100% 来自"新增的残缺记录 + 已知 p2 空 URL"，0 项来自基座。** 现有报告把锅甩给"基座骨架、预期内"，既与"基座 0 ERROR"的事实矛盾，也掩盖了真正的管线缺陷。

## 三、🔴 致命问题 2：新增记录"出生即残缺"

15 条含 ERROR 的新增记录，根因是**合并工具 `add_record` 路径在 incoming 是分片补丁时不回填完整 schema 骨架**。实锤样例（直接取自 v2 当前内容）：

`google:gemini-3-pro:base` 在 v2 中**只有 3 个顶层键**：
```
顶层键: [schema_version, model_id, benchmarks]
缺失顶层键: [basic_info, architecture, pricing, modality, meta]
```
——**连厂商名、发布日期、参数、定价、模态、meta 全都没有**，只剩一个 ID 加几条 Arena 分数。
`meituan:longcat-flash:base` 同样只有 `{schema_version, model_id, benchmarks}`。

（并非全部残缺：`moonshot:kimi-k2:base` 八键齐全，说明问题出在"用分片补丁新增模型"这条路径，而非所有新增。）

**这 15 条就是当前 v2 的 ERROR 主体。** 它们不是"基座预期内的空骨架"，而是"合并管线生产出来的不合格产品"。每通过 p1/p2 这类分片补丁新增一个模型，就会再产一条这种废记录。

**附带打脸**：`盘点与待改清单.md` 称"incoming 引入的硬错误仅 10 条"——实际是 **17 条记录含 ERROR（15 新增 + 2 基座的 p2 空 URL）**，不只是 10 条。

## 四、🔴 致命问题 3：2 条"已验证"是假验证

`verification_status` 分布：

| 状态 | 数量 | 占比 |
|------|------|------|
| 待验证 | 924 | 98.2% |
| None（字段都没有） | 15 | 1.6% |
| 已验证 | 2 | 0.2% |

抽查那 2 条"已验证"：

- `anthropic:claude-3-sonnet:base`：`verified_at = None`，notes 只是"G1 子代理补充……置信度 T0"
- `openai:gpt-4.1-mini:base`：`verified_at = None`，同上

**标了"已验证"却没有验证时间、没有验证依据，等于把状态字段当装饰贴了个标签。** 另外 15 条连状态都没有（None），连"待验证"都没标。整个 verification 维度形同虚设。

跑分内部：

- `self_reported`（自报跑分）：**22 条条目 / 仅 12 条记录**——基本空白

**空壳统计**：

换句话说：v2 的"实体"是一个 identity + 参数（继承自 v1 的骨架）再加一大包 Arena 分数；**定价、多模态、定位这三类用户最常问的信息，几乎整体缺席。** 叫它"v2 数据库"是抬举了，叫"带 Arena 分数的模型名单"更准确。

## 六、🟡 严重问题 5：notes 是占位符海洋，不是数据

- **926 / 941（98.4%）** 的记录 notes 里含有占位符语料（`待补`/`未含`/`未披露`/`缺失`/`需另行采集`/`来源数据未含`……）
- 占位符 notes 字段累计 **5531 处**

也就是说，库里绝大多数文本内容的真实含义是"这一项我没采到"，而不是"这一项的数据如下"。**占位符不是数据，是 TODO。** 把这种库当成品交付，等于交了一本写满"此处待补"的空表格。

## 七、🟡 严重问题 6：collected_at 全员硬编码同日

- 926 条 `collected_at` 全是 `2026-08-24`（同一天）
- 15 条为 None

这是 `TEST_REPORT.md` 里早就报过的 **P2 问题（newer_wins 同日平局静默保旧）**，到现在**没根治**。后果：你无法区分"哪条是今天真采的、哪条是去年骨架带过来的"，而合并/更新逻辑恰恰依赖 `collected_at` 判新旧——依赖一个全员相等的字段，判新旧就是瞎判。

## 十、修复建议（按优先级，不客气版）

1. **【必须，阻断级】修合并工具 `add_record`**：新增记录必须按 schema 1.1 全骨架初始化（所有必采键显式 `null`），分片补丁只填对应字段。否则每加一个模型就产一条"只有 ID + 分数"的废记录。
2. **【必须】把 15 条新增残缺记录补齐**：至少补 `basic_info`（vendor/release_date）、`architecture`、`pricing`(全 null)、`modality`(全 null)、`meta`；或直接退回重采。现在 `google:gemini-3-pro:base` 这种连厂商名都没有的记录不该存在于"数据库"里。
3. **【必须】清理假验证**：2 条"已验证"要么补 `verified_at` + 依据，要么改回"待验证"；15 条 None 补"待验证"。
4. **【严重】collected_at 改真实时间戳（带时分秒）**：否则更新/合并逻辑永远是瞎子。这是已知 P2，别再拖。
5. **【严重】正视"占位符海洋"**：5531 处"待补"不是成果。要么组织真正的一轮全字段采集（优先定价/模态/定位），要么在库层面**诚实标注"这是骨架库、非成品库"**，别拿占位符当内容交付。
6. **【内容】补 payload**：定价 5.3% / 模态 6% / 定位 0.2% 这三个字段不补齐，这个库对"选模型"毫无实用价值。建议作为阶段 3 核心目标，而不是"留待阶段3 质检"轻轻带过。
7. **【治理】修正自查报告**：把 184 ERROR 的归因改成"集中在新增残缺记录、属管线缺陷"，别再写成"基座预期内"。
