### 新发现的两个阻塞点（已写入文档）

1. **超长文件名 Windows 260 上限**：多机构联合署名的 batch_id 最长 479 字符，标准命名 `<batch_id>__<vendor>__<model>__<variant>` 路径可达 1041 字符，写盘直接 OSError [Errno 22]。全库 702 个应产出文件中 **26 个超限、涉 19 个批次**。
   解法：路径 >250 字符时降级为 `<bNNwM>__<model>__<variant>.jsonl`。已核验 305 个批次短标识**零冲突**，降级后最长 133 字符。
2. **平台 subagent 并发上限 429**：一次派 8 个会陆续触发 `429 queue.userLimit`；降到 3 个一组可正常跑；完全占满时连 1 个都派不出（连续 5 次失败）。
   解法：无法派发时**必须把已 claim 的批次回退 pending** 并清空 claimed_by/claimed_at + 留痕，否则虚占进度阻塞他人。本轮末期 8 批（b69w1/b70w1/b71w1/b72w1/b73w1/b74w1/b87w1/b88w1）已按此回退。

### 踩坑记录

- `xargs git add -f` 报「environment is too large for exec」；改用 Python `subprocess` 逐个 add。
- 用 Windows Python 写文件清单再让 bash `while read` 读取，行尾会带 `\r`，导致 git 报 `pathspec 'xxx.jsonl?' did not match`；写文件时要 `newline='\n'` 或读取时 `strip()`。
- `git pull --rebase` 遇他人未提交改动会直接失败（不自动 stash）；因 trae 不 push，远程始终无新提交，可直接 commit+push 跳过 pull。
